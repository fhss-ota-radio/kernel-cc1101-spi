# 라즈베리파이 실기기에 `cc1101.ko` 올리기 — 빌드/적재 가이드

`README.md`의 "빌드 및 적재" 섹션은 표준 라즈베리파이 OS를 그대로 쓰는
경우를 가정한 간단 버전입니다. 이 문서는 **커스텀(비표준) 커널을 쓰는
보드**(우리 프로젝트의 파이 2대가 여기 해당)에서 실제로 겪은 문제와 해결
과정을 담은 상세 가이드입니다. 2026-08-16에 실기기 2대(pi24, pi06)에서
`/dev/cc1101`을 성공적으로 띄운 전체 과정을 정리했습니다.

---

## 0. 먼저 확인할 것 — 커널이 표준인가 커스텀인가

```sh
uname -r
```

이 값이 라즈베리파이 재단 공식 배포 커널(`apt`로 설치되는 버전)과
일치하면 `README.md`의 간단 절차만으로 충분합니다. 우리 보드처럼
`6.12.92-v7l+` 같은 값이면서 `cat /proc/version`에 `(ubuntu@어떤호스트)`
같은 빌드 계정이 찍혀 있다면, 별도로 크로스컴파일된 **커스텀 커널**입니다
— 아래 절차를 따라야 합니다.

**왜 이게 중요한가**: 커널 모듈(`.ko`)은 실행 중인 커널과 정확히 같은
버전·설정으로 빌드되어야만 로드됩니다. `apt`가 제공하는 "가장 비슷한"
커널 헤더로 빌드해도, vermagic(모듈에 박히는 커널 버전 식별 문자열)이나
MODVERSIONS(심볼별 체크섬, 커널 설정에 따라 켜짐)가 안 맞으면
`insmod`가 `Invalid module format`으로 거부합니다. `insmod -f`(강제 로드)도
이 커널은 `CONFIG_MODULE_FORCE_LOAD`가 꺼져 있어서 안 통합니다.

## 1. 정확히 일치하는 커널 소스트리 찾기

커스텀 커널을 빌드한 사람에게 "어디서 크로스컴파일했는지" 물어보세요.
우리 프로젝트는 별도 우분투 서버(`ubuntu@ubuntu24`)에서
`arm-linux-gnueabihf-gcc`로 크로스컴파일된 것이었고, 그 서버의
`/home/ubuntu/pi_bsp/kernel/linux`가 정확히 일치하는 소스트리였습니다.

확인 방법:
```sh
cat <커널소스경로>/include/config/kernel.release
```
이 값이 파이의 `uname -r`과 **완전히 동일**해야 합니다. `.config` 파일도
존재해야 합니다.

## 2. 크로스컴파일

```sh
cd kernel-cc1101-spi
make ARCH=arm CROSS_COMPILE=arm-linux-gnueabihf- KDIR=<위에서 찾은 커널소스경로>
modinfo cc1101.ko | grep vermagic   # uname -r과 정확히 일치하는지 확인
```

`ARCH=arm`: 32비트 ARM 아키텍처로 빌드하라는 뜻(파이가 32비트 OS인 경우).
`CROSS_COMPILE=arm-linux-gnueabihf-`: 이 접두사가 붙은 툴체인
(`arm-linux-gnueabihf-gcc` 등)을 쓰라는 뜻 — 빌드 서버(보통 x86_64)가 아닌
ARM용 바이너리를 만들기 위함. `KDIR`: 1번에서 찾은 정확히 일치하는 커널
소스 디렉터리.

## 3. 디바이스트리 오버레이 빌드

`dts/cc1101-overlay.dts`를 컴파일합니다:

```sh
which dtc || sudo apt install -y device-tree-compiler
dtc -@ -I dts -O dtb -o cc1101.dtbo dts/cc1101-overlay.dts
```

> **주의**: 이 파일이 예전에 `#include <dt-bindings/gpio/gpio.h>`를 쓴 적이
> 있었는데, `dtc`는 C 전처리기가 아니라서 이 구문 자체를 못 읽고
> `syntax error`를 냅니다. 지금 레포 버전은 이미 리터럴 값(`0`)으로
> 고쳐져 있어 문제없이 컴파일됩니다 — 혹시 옛날 버전을 쓰고 있다면
> 최신 `dts/cc1101-overlay.dts`로 갱신하세요.

## 4. 파이에 설치 (Raspberry Pi OS bookworm/trixie 기준 — `/boot/firmware/`)

`README.md`는 `/boot/overlays/`, `/boot/config.txt`로 안내하는데, 최신
Raspberry Pi OS(bookworm 이후)는 부트파티션이 `/boot/firmware/`에
마운트됩니다. 실제 경로를 꼭 확인하세요:

```sh
ls /boot/firmware/overlays/ 2>/dev/null || ls /boot/overlays/
```

```sh
sudo cp cc1101.dtbo /boot/firmware/overlays/
echo "dtparam=spi=on" | sudo tee -a /boot/firmware/config.txt
echo "dtoverlay=cc1101" | sudo tee -a /boot/firmware/config.txt
sudo reboot
```

재부팅 후:
```sh
sudo insmod cc1101.ko
dmesg | grep -i cc1101      # "CC1101 감지됨", "/dev/cc1101 등록 완료" 확인
ls /dev/cc1101
```

## 5. GDO0/GDO2 배선 — 보드마다 다를 수 있음, 반드시 실측 확인

`cc1101-overlay.dts`의 기본값은 **GDO0=GPIO24, GDO2=GPIO25**입니다.
2026-08-16 실기기 테스트에서 이 기본값이 pi24/pi06 두 보드 모두에서
정상 동작함을 확인했습니다 (`/proc/interrupts`로 `cc1101-gdo0`
인터럽트가 송신 시도 횟수만큼 정확히 증가하는 것으로 검증).

**주의**: 별도로 전달받은 배선표는 GDO0=GPIO25, GDO2=GPIO24로 반대였는데,
실기기 테스트 결과 이 표가 틀렸거나 최소 우리가 쓴 보드와는 다름 —
새 보드를 배선할 때는 아래 방법으로 직접 검증하세요.

재컴파일 없이 오버레이 파라미터로 다른 핀 값을 바로 테스트할 수 있습니다:
```sh
sudo sed -i 's/dtoverlay=cc1101$/dtoverlay=cc1101,gdo0_pin=<값>,gdo2_pin=<값>/' /boot/firmware/config.txt
sudo reboot
```

어느 값이 맞는지 확인하는 방법: 커널 모듈 로드 후 `/proc/interrupts`에서
`cc1101-gdo0`/`cc1101-gdo2` 카운트를 기록해두고, 송신(`write()`)이나
수신 시도를 몇 번 해본 뒤 다시 확인 — 실제로 카운트가 증가하는 쪽이
맞는 배선입니다:
```sh
grep cc1101 /proc/interrupts
```

## 6. 알려진 버그 (이미 이 레포에 수정 반영됨, `feature/cc1101_V1` 브랜치)

| 증상 | 원인 | 수정 커밋 |
|---|---|---|
| 크로스컴파일 시 `incompatible pointer type` 에러 | `cc1101_remove()`가 `int` 반환 — 커널 6.5+는 `void`여야 함 | `0aaa0c2` |
| `dtc` 컴파일 시 `syntax error` | `dts/cc1101-overlay.dts`가 dtc가 못 읽는 `#include` 사용 | `403ce99` |
| 송신은 되는데 수신 쪽이 거의 항상 무응답 | `cc1101_core.c`의 `PKTCTRL1` 기본값이 CC1101 하드웨어 주소필터를 켜놓음(`ADR_CHK`) — `ota_protocol.h` 패킷은 이 필터가 기대하는 "주소 바이트"를 안 써서 대부분 하드웨어 레벨에서 버려짐 | `9d1e045` |

**`PKTCTRL1` 버그 상세**: CC1101의 `ADR_CHK` 기능은 수신 패킷의 첫 페이로드
바이트를 자기 `ADDR` 레지스터와 비교해서 안 맞으면 CRC 검사 전에
하드웨어에서 버립니다. `ota_protocol.h`의 모든 패킷은 첫 바이트가
"패킷 타입"(`OTA_PKT_START` 등)이지 주소가 아니므로, 이 필터가 켜져
있으면 대부분의 패킷이 걸러집니다. 이 프로젝트의 주소/라우팅 판단은
애초에 `ota_protocol.h` 상위 계층(`session_id`, `device_id` 필드)에서
소프트웨어로 처리하도록 설계되어 있어 CC1101 하드웨어 필터가 불필요합니다
— `cc1101_default_regs[]`의 `PKTCTRL1`을 `0x0D`(필터 켬)에서
`0x0C`(필터 끔)로 변경해 해결했습니다.

## 7. 진단 팁

- `dmesg | grep -i cc1101` — probe 성공 여부, 경고 확인
- `grep cc1101 /proc/interrupts` — GDO0(송신완료)/GDO2(수신) 인터럽트가
  실제로 얼마나 울리는지 카운터로 확인 (핀 배선 검증에도 유용)
- 이 커널은 `CONFIG_DYNAMIC_DEBUG`가 꺼져 있어서 `dev_dbg()` 로그가
  `dmesg`에 전혀 안 보입니다 — 진단이 필요하면 임시로 `dev_warn()`으로
  올려서 확인 후 되돌리세요.

## 8. 2026-08-16 최종 결과 — GDO2 미스터리 해결(안테나) + 팀 간 싱크워드 충돌 발견

> 이 절은 하루 동안 원인을 잘못 짚었다가 바로잡은 기록입니다. 같은 함정에
> 빠지지 않도록 결론뿐 아니라 **틀렸던 추론도 남깁니다.**

### 8-1. "GDO2 인터럽트가 한 번도 안 울린다" — 오실로스코프 필요 없었음, 안테나 불량이었다

한동안 이 가이드에는 *"GDO2 펄스 폭이 너무 짧아 GPIO 엣지 인터럽트가 못
잡는 것 같다, 오실로스코프로 확인해야 한다"* 고 적혀 있었습니다. **틀렸습니다.**

실제 원인은 **수신측(pi06) 안테나 불량**이었습니다. 헐거운 게 아니라 안테나
자체가 죽어 있었고, 다른 안테나로 교체하니 GDO2 인터럽트가 정상적으로
울리기 시작했습니다(`cc1101-gdo2` 카운트 1182까지 증가, `[임시디버그] 패킷
큐에 넣음` 로그도 정상 출력).

**진단 힌트 — 이 비대칭이 보이면 안테나부터 의심하세요:**

> **"송신은 되는데 수신만 안 된다"**
>
> 송신은 칩이 신호를 밀어내는 거라 안테나가 부실해도 근거리면 상대가 받습니다.
> 반면 수신은 공기 중의 미약한 신호를 긁어모아야 해서 안테나 성능에 훨씬
> 민감합니다. 그래서 안테나가 죽으면 "TX 정상 / RX 사망" 패턴이 나옵니다.

### 8-2. 진짜 큰 문제 — 팀 전체가 같은 싱크워드를 쓰고 있었다

안테나를 고치고 나니 이번엔 **다른 팀원들의 패킷**이 쏟아져 들어왔습니다:

```
46 48 53 53 01 01 00 00 ...    ← ASCII로 "FHSS"
A5 01 02 00 02 00 00 14 14 ... ← 49byte짜리, 다른 프로토콜
```

다들 TI 레퍼런스 기본 설정을 그대로 쓰다 보니 **433.92MHz + 싱크워드
`0xD3/0x91`까지 전부 겹쳐 있었습니다.** 남의 패킷이 CRC까지 통과해
정상 패킷으로 올라왔고, 이 드라이버의 RX 큐(512byte)를 가득 채워
**우리 패킷이 도착해도 전부 폐기**됐습니다.

**해결**: `cc1101_core.c`의 `cc1101_default_regs[]`에서 싱크워드를
OTA 전용 값 **`SYNC1=0x2D, SYNC0=0xD4`** 로 분리했습니다. CC1101은
싱크워드가 다르면 **하드웨어 단에서 무시**합니다 — 인터럽트도 안 울리고
FIFO에도 안 들어오므로, 소프트웨어 필터링보다 훨씬 깨끗하고 부담이 0입니다.
적용 후 남의 트래픽이 완전히 사라진 것을 확인했습니다.

> **[중요] 같은 값이 `gateway-ota/OTA_System/transport/spidevtransport.cpp`
> 의 레지스터 배열에도 들어가 있어야 합니다.** 한쪽만 바꾸면 두 경로가
> 서로 통신하지 못합니다.
>
> **[팀 공유 필요] 다른 팀도 각자 고유 싱크워드를 쓰셔야 완전히 격리됩니다.**
> 누가 어떤 주파수/싱크워드/채널을 쓰는지 정리된 표를 만들어 관리할 것.

### 8-3. 드라이버 수정 2건 (RX 큐 관리)

**① `cc1101_open()`에서 kfifo 비우기**
드라이버는 `probe()`에서 RX 진입한 순간부터 계속 수신해 큐에 쌓지만, 유저
프로그램은 한참 뒤에 붙습니다. 그 사이 쌓인 건 이미 지나간 데이터라
쓸모없는데 자리만 차지해 새 패킷을 막습니다. 열 때 비우도록 수정.

**② 큐가 찼을 때 "오래된 것"부터 버리기**
이전엔 자리가 없으면 방금 받은 패킷을 버렸습니다. 그러면 **한 번 차는
순간부터 영원히 새 패킷이 못 들어와** 수신이 완전히 마비됩니다. 통신에서는
오래된 데이터가 새 데이터보다 가치가 낮으므로 지나간 것을 밀어내도록 변경.

### 8-4. 아직 안 되는 것 — 커널 RX 패킷 경계 밀림

교차 테스트(pi24=커널 드라이버 송신, pi06=spidev 수신)로 **커널 드라이버의
송신(TX)은 정상**임을 확인했습니다 — 핸드셰이크 성공, `OTA_START` 정상 디코딩.

남은 문제는 **수신(RX)의 패킷 경계**입니다. 깨진 패킷 꼬리에 다음 패킷의
프리앰블(`AA AA AA`)과 싱크워드(`2D D4`)가 딸려 들어와 있습니다. 한 번 읽을 때
패킷 하나를 넘어 다음 패킷까지 같이 읽는다는 뜻이고, 디코딩 성공률이 4개 중
1개꼴인 것도 수신이 송신 속도를 못 따라가 FIFO에 겹쳐 쌓이는 모습과 일치합니다.

**다음에 볼 사람이 할 것 (우선순위 순)**

1. 송신 간격을 늘려 재현 여부 확인
   (`ota_smoke_send /dev/cc1101 <bin> ffffffff 40` — 4번째 인자가 청크 간 ms)
   → 수신율이 오르면 "수신이 못 따라감" 확정
2. `cc1101_handle_rx_packet()`의 `out_rearm`이 `SFRX` 없이 `SRX`만 하는 것 검토.
   `SpidevTransport`는 매번 `SIDLE; SFRX; SRX`로 FIFO를 완전히 비우고 재시작하는데,
   이 차이가 잔여물 누적을 만들 수 있음
3. 급하면 `SpidevTransport`(`gateway-ota/OTA_System/transport/spidevtransport.*`)
   사용 — 1067/1067 전량 수신으로 검증된 경로

### 8-5. 진단 도구 — 추측하지 말고 재세요

`tools/cc1101_diag.c`를 추가했습니다. `CC1101_IOC_READ_REG` / `GET_STATUS`
ioctl로 **칩 내부를 직접 읽습니다.**

```sh
gcc -O2 -o cc1101_diag tools/cc1101_diag.c -I.
sudo ./cc1101_diag --set-rx
```

- 핵심 레지스터 16개를 기대값과 비교 → 설정이 제대로 써졌는지 즉시 확인
- `MARCSTATE`(칩 상태머신) 출력 → `0x0D`면 수신 대기 정상

저희는 이 도구를 만들고 나서야 "설정 문제 아님 / 칩은 RX 상태 정상"을
확정하고 범위를 좁힐 수 있었습니다. **RF 디버깅은 추론보다 계측이 압도적으로
빠릅니다.**

### 8-6. 원인 계층을 로그로 가르는 기준

원인 후보가 안테나→전원→배선→커널→유저공간으로 넓게 퍼져 있어 헤매기 쉽습니다.
이 기준 하나가 시간을 가장 많이 아껴줬습니다:

| 관찰 | 의미 | 볼 곳 |
|---|---|---|
| `/proc/interrupts` 카운트가 **아예 안 올라감** | 전파가 칩까지 안 옴 | **물리 계층** — 안테나, 전원, 배선 |
| 카운트는 올라가는데 **디코딩이 깨짐** | 신호는 오는데 읽기가 잘못됨 | **소프트웨어** |

그리고 **송수신 역할을 서로 바꿔서**(A→B, B→A) 테스트하면 "어느 방향/어느
보드가 죽었는지"를 빠르게 좁힐 수 있습니다. 두 파이는 독립이라 한쪽만
spidev 모드로 두는 교차 테스트도 가능합니다 — 이걸로 TX/RX 중 어느 쪽이
문제인지 갈랐습니다.
