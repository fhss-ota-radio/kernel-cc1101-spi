# CC1101 트러블슈팅 가이드

> 2026-08-16 실기기 디버깅에서 실제로 겪은 것들을 증상별로 정리했습니다.
> 이 프로젝트(`kernel-cc1101-spi` + `gateway-ota`)뿐 아니라 CC1101을 쓰는
> 다른 팀 작업에도 대부분 적용됩니다.
>
> 하루를 태워서 얻은 것들이라, **저희가 헤맨 순서 그대로가 아니라 빨리
> 좁혀지는 순서로** 재배치했습니다.

---

## 0. 시작하기 전에 — 원인 계층을 먼저 가르세요

CC1101 문제는 원인 후보가 **안테나 → 전원 → 배선 → SPI → 칩 설정 → 커널
인터럽트 → 큐 관리 → 유저공간**으로 넓게 퍼져 있습니다. 아무 데나 손대면
하루가 날아갑니다(실제로 그랬습니다).

**이 두 줄이 시간을 가장 많이 아껴줍니다:**

```sh
grep cc1101 /proc/interrupts        # 인터럽트가 울리는가?
sudo ./cc1101_diag --set-rx         # 칩 설정/상태가 정상인가?
```

| 관찰 | 의미 | 어디를 볼 것인가 |
|---|---|---|
| 인터럽트 카운트가 **전혀 안 올라감** | 전파가 칩까지 안 옴 | **1장** — 안테나·전원·배선 |
| 카운트는 올라가는데 **데이터가 깨짐** | 신호는 오는데 해석이 틀림 | **3~4장** — 설정·읽기 타이밍 |
| 데이터는 멀쩡한데 **유저공간에 안 올라옴** | 큐/전달 문제 | **5장** |
| 카운트가 **비정상적으로 폭증** | 인터럽트 폭주 | **6장** |

> **핵심 원칙: 추측하지 말고 재세요.** 저희는 `cc1101_diag`를 만들고 나서야
> "설정 문제 아님 / 칩은 RX 정상"을 확정하고 범위를 좁힐 수 있었습니다.
> 진단 도구를 먼저 만드는 게 돌아가는 길처럼 보여도 실제로는 지름길입니다.

## 1. 아무것도 안 잡힘 — 인터럽트 카운트가 0

`grep cc1101 /proc/interrupts`를 30초 간격으로 두 번 찍어 숫자가 그대로면
이 장입니다.

```sh
grep cc1101 /proc/interrupts; sleep 30; grep cc1101 /proc/interrupts
```

### 1-1. 안테나 (가장 흔함 — 하루에 4번 겪었습니다)

> **⚠️ 결정적 진단 힌트: "송신은 되는데 수신만 안 된다"면 안테나입니다.**
>
> 송신은 칩이 신호를 밀어내는 거라 안테나가 부실해도 근거리면 상대가 받습니다.
> 반면 수신은 공기 중의 미약한 신호를 긁어모아야 해서 안테나 성능에 훨씬
> 민감합니다. 그래서 안테나가 죽으면 **"TX 정상 / RX 사망"** 이라는 비대칭이
> 나옵니다. 이 패턴을 보면 다른 걸 보기 전에 안테나부터 확인하세요.

확인 순서:
1. SMA 커넥터를 손으로 꽉 조입니다 (헐거운 경우가 제일 많음)
2. **다른 안테나로 교체해봅니다** — 헐거운 게 아니라 **안테나 자체가 불량**인
   경우가 실제로 있었습니다. 교체하니 즉시 해결됐고, 그 전까지 반나절을
   소프트웨어 문제로 오해했습니다
3. 두 보드를 30cm 이내로 붙여서 재시도

### 1-2. 전원

- CC1101은 **최대 3.6V**입니다. 5V를 넣으면 칩이 타버립니다
- 파이의 3.3V 핀에서 직접 받으면 송신 순간의 전류 요구를 못 받쳐줄 수 있습니다
- **브레드보드 전원모듈(MB102/HW-131) 주의사항**:
  - 전압 점퍼가 **3.3V**에 꽂혀 있는지 확인 (5V면 칩 손상)
  - **3.3V 출력 지점이 여러 곳인데 서로 연결하면 발열합니다** — 한 곳만 쓰세요
    (실제로 가운데 핀과 레일 점퍼를 이어놨다가 모듈이 뜨거워졌습니다)
  - **파이와 GND 공유 필수** — 전원만 따로 주고 GND를 안 묶으면 SPI/GDO 신호의
    기준 전압이 안 맞아 더 이상해집니다
  - 연결 전에 멀티미터로 3.3V가 나오는지 먼저 재보세요

### 1-3. 칩이 RX 상태가 아님

```sh
sudo ./cc1101_diag --set-rx
```
`MARCSTATE`를 봅니다:
- `0x0D (RX)` → 정상. 이 장의 다른 항목을 보세요
- `0x01 (IDLE)` 등 → RX 진입 자체가 실패. `startRx()` / `CC1101_IOC_SET_RX`
  호출 경로를 확인하세요

### 1-4. 배선 — GDO0/GDO2 핀 번호

> **⚠️ 팀에 공유된 배선표가 틀렸습니다.**
> 전달받은 표는 GDO0=GPIO25 / GDO2=GPIO24였는데, **실기기 검증 결과 반대**
> 였습니다. 레포 기본값(**GDO0=GPIO24, GDO2=GPIO25**)이 맞습니다.
> 표대로 스왑하면 `cc1101 spi0.0: TX 타임아웃`이 납니다.

새 보드를 배선할 때는 표를 믿지 말고 직접 검증하세요. 재컴파일 없이
오버레이 파라미터로 바꿔 테스트할 수 있습니다:

```sh
sudo sed -i 's/^dtoverlay=cc1101$/dtoverlay=cc1101,gdo0_pin=<값>,gdo2_pin=<값>/' \
  /boot/firmware/config.txt
sudo reboot
# 송신/수신을 시도하면서 어느 쪽 카운트가 실제로 늘어나는지 확인
grep cc1101 /proc/interrupts
```

### 1-5. SPI 신호 품질

`cc1101_diag`에서 **레지스터 값이 기대값과 다르거나** `PARTNUM`이 `0x00`이
아닌 값(예: `0x0f`)으로 읽히면 SPI 통신이 깨지고 있습니다. CC1101의
`PARTNUM`은 항상 `0x00`이어야 합니다.

- 브레드보드 + 점퍼선은 4MHz쯤에서 신호가 흐트러질 수 있습니다
- 오버레이로 클럭을 낮춰 테스트: `dtoverlay=cc1101,speed=1000000`
- SPI 4선(MOSI/MISO/SCK/CSN) 접촉 재확인

## 2. 남의 패킷이 잡힘 / 우리 패킷이 밀려남

### 증상

`dmesg`나 수신 로그에 이런 것들이 보입니다:

```
46 48 53 53 01 01 00 00 ...    ← ASCII로 "FHSS"
A5 01 02 00 02 00 00 14 14 ... ← 49byte짜리, 다른 프로토콜
```

그리고 커널 로그에:
```
cc1101 spi0.0: RX 소프트웨어 큐 가득 참, 패킷 폐기
```

### 원인

**같은 프로젝트의 다른 팀 장비와 주파수·싱크워드가 겹쳤습니다.** 다들 TI
레퍼런스 기본 설정을 그대로 쓰면 `433.92MHz + SYNC 0xD3/0x91`로 전부 동일해
집니다. 남의 패킷이 **CRC까지 통과해 정상 패킷으로 올라와** 수신 버퍼를
채우고, 그러면 우리 패킷은 도착해도 폐기됩니다.

실측: GDO2 인터럽트 1182회 중 대부분이 남의 패킷이었습니다.

### 해결 — 싱크워드 분리

CC1101은 싱크워드가 다르면 **하드웨어 단에서 무시**합니다(인터럽트도 안 울리고
FIFO에도 안 들어옴). 소프트웨어 필터링보다 훨씬 깨끗하고 CPU/큐 부담이 0입니다.

| 용도 | SYNC1/SYNC0 | 상태 |
|---|---|---|
| OTA | `0x2D` / `0xD4` | 적용 완료 |
| 음성/기타 | 협의 필요 | 미정 |

- 싱크워드는 **1과 0이 균형 잡히고(8:8) 반복 패턴이 없어야** 오검출(false sync)이
  적습니다. `0x2DD4`가 이 조건을 만족합니다
- **바꿀 곳이 두 군데입니다**: `kernel-cc1101-spi/cc1101_core.c`의
  `cc1101_default_regs[]`, 그리고 `gateway-ota`의
  `OTA_System/transport/spidevtransport.cpp` 레지스터 배열.
  **한쪽만 바꾸면 두 경로가 통신하지 못합니다**

> **팀 차원 과제: 누가 어떤 주파수/싱크워드/채널을 쓰는지 정리된 표가 없습니다.**
> 이번 문제가 그것 때문에 생겼으니 만들어두면 좋겠습니다.

### 채널 분리를 쓸 경우 — 밴드 제약 주의

싱크워드로 충분하지 않으면 채널(`CHANNR`)도 옮길 수 있는데, **함부로 큰 값을
넣으면 안 됩니다.**

```
주파수 = 433.92MHz + CHANNR × 채널간격(약 200kHz)
```

- 국내 433MHz ISM 밴드는 **433.05~434.79MHz** → **채널 4(434.72MHz)가 상한**
- 채널 5(434.92MHz)부터는 밴드 이탈 = **전파법 위반**
- 큰 값(예: 200)은 473.92MHz로 **CC1101 지원 밴드(387~464MHz)조차 벗어나
  PLL이 락을 못 걸어 송수신이 통째로 죽습니다**
- 수신 채널 필터 대역폭이 약 102kHz이므로, 채널 4는 채널 0과 800kHz(대역폭의
  약 8배) 떨어져 서로 보이지 않습니다

## 3. 패킷은 오는데 CRC가 계속 깨짐

`gdo0`은 올라가는데 `gdo2`(CRC OK 수신)는 0인 상태입니다.

- **안테나 상태 재확인** (1-1) — 신호가 약하면 sync word는 잡히지만 CRC를
  못 넘깁니다
- 두 보드를 가까이 붙여서 재시도
- `cc1101_diag`로 양쪽 레지스터가 **동일한지** 확인 — 특히 `FREQ2/1/0`,
  `MDMCFG2/3/4`, `DEVIATN`, `SYNC1/SYNC0`, `CHANNR`. 하나만 달라도 복조가
  안 됩니다
- `PKTCTRL1`의 `CRC_AUTOFLUSH`가 켜져 있으면 CRC 실패 패킷은 FIFO에서 자동
  삭제됩니다 → `RXBYTES=0`으로 보일 수 있습니다(정상 동작)

## 4. 패킷 내용이 밀리거나 섞임

### 증상 A — 길이바이트가 페이로드에 섞임

```
디코딩 실패: 3C 02 EE BE 07 51 ...
             ↑ 길이바이트(0x3C=60)가 데이터 앞에 붙어 1바이트씩 밀림
```
`session_id`가 `0x5107beee` → `0x07beeeee`처럼 시프트돼 보입니다.

**원인**: 가변길이 모드에서 RX FIFO는 무선으로 바이트가 도착하는 대로 **조금씩**
채워집니다(`RXBYTES`가 수신 중 계속 증가). 그런데 `RXBYTES != 0`이기만 하면
곧바로 길이바이트+본문을 읽어버리면, 아직 안 온 부분까지 읽으려다 FIFO
언더플로로 쓰레기 값이 섞입니다.

**해결**: **`RXBYTES`가 더 이상 늘어나지 않을 때(= 패킷 완전 도착)까지 기다린
다음** 읽습니다. 우리 패킷은 전부 64byte FIFO에 들어가는 크기라 이 방식이
안전합니다. → 이 수정으로 수신율이 **78.5% → 100%** 로 올랐습니다.

> 이 21.5% 손실을 한동안 "무선 환경 손실이라 어쩔 수 없다"고 판단해 문서에까지
> 적었는데, **전부 이 소프트웨어 버그였습니다.** RF 문제로 단정하기 전에
> 소프트웨어를 의심하세요.

### 증상 B — 다음 패킷의 프리앰블이 딸려 들어옴

깨진 패킷 꼬리에 `AA AA AA AA` (프리앰블) + `2D D4` (싱크워드)가 보입니다.
디코딩 성공률이 4개 중 1개꼴로 떨어집니다.

**원인**: 수신이 송신 속도를 못 따라가 FIFO에 여러 패킷이 겹쳐 쌓입니다.

**해결(현재)**: 송신 청크 간 대기를 늘립니다.
```sh
sudo ./ota_smoke_send /dev/cc1101 <bin> ffffff 40   # 마지막 인자가 대기 ms
```
10ms → 40ms로 늘리니 100%가 됐습니다. **근본 해결은 수신 처리량 개선이며
남은 과제입니다.** `out_rearm`에서 `SFRX` 없이 `SRX`만 하는 것이 관련 있을
수 있습니다 — 유저공간 구현은 매번 `SIDLE; SFRX; SRX`로 완전히 비우고
재시작합니다.

## 5. 커널까지는 오는데 유저공간에 안 올라옴

### 증상

`dmesg`에 `[임시디버그] 패킷 큐에 넣음`은 찍히는데 앱 화면에는 아무것도 안
나옵니다. 또는:
```
cc1101 spi0.0: RX 소프트웨어 큐 가득 참, 패킷 폐기
```

### 원인과 해결

두 가지 버그가 있었고 둘 다 수정했습니다:

1. **`cc1101_open()`이 RX 큐를 비우지 않았음** — 드라이버는 `probe()`에서 RX에
   들어간 순간부터 계속 수신해 큐에 쌓지만, 유저 프로그램은 한참 뒤에 붙습니다.
   그 사이 쌓인 건 이미 지나간 데이터라 쓸모없는데 자리만 차지해 새 패킷을
   막았습니다 → 열 때 비우도록 수정

2. **큐가 찼을 때 "새" 패킷을 버렸음** — 그러면 **한 번 차는 순간부터 영원히
   복구가 안 됩니다**(수신 완전 마비). 통신에서는 오래된 데이터가 새 데이터보다
   가치가 낮으므로 **오래된 것부터 버리도록** 변경

> 이 정책은 용도에 따라 다를 수 있습니다. 실시간 스트림(음성)에는
> drop-oldest가 맞지만, 손실이 치명적인 용도라면 반대일 수 있습니다.

### 앱이 큐를 못 읽는 경우

- 드라이버는 **동시에 하나만 open**을 허용합니다(`-EBUSY`). 다른 프로그램이
  `/dev/cc1101`을 잡고 있으면 열리지 않습니다 — 진단 도구와 수신 프로그램을
  같이 못 돌리는 이유입니다
- `poll()`이 `POLLIN`을 안 주는지 확인 (`cc1101_poll`이 `kfifo_is_empty`로
  판단합니다)

## 6. 인터럽트 폭주 (IRQ storm)

### 증상

```
72:   77285524   ...   cc1101-gdo0     ← 7,728만 회
```
정상은 수십~수백 회입니다. 폭주하면 CPU를 다 잡아먹어 **어떤 테스트도 결과를
믿을 수 없습니다.**

### 원인 (실제로 겪은 것)

**송신 완료 후 `SRX`를 명시적으로 안 하면** 칩이 안정된 RX 상태로 수습되지
않고 GDO0이 계속 토글하는 상태에 남습니다.

`MCSM1=0x3F`가 TXOFF_MODE=11(송신 끝나면 자동 RX 복귀)이라 수동 `SRX`가
불필요해 보이지만, **자동 복귀만 믿으면 안 됩니다.** `cc1101_gdo0_thread()`의
TX 완료 경로에서 `cc1101_enter_rx()`를 반드시 호출하세요.

> 판별 힌트: 폭주가 **송신을 수행한 쪽에서만** 발생하고 수신 전용 보드는
> 정상이면 이 문제입니다.

### 복구

`rmmod`만으로는 부족할 수 있습니다. **재부팅**하세요.
`/proc/interrupts`의 카운터는 GPIO IRQ 디스크립터가 재사용되므로
`rmmod`/`insmod`로 리셋되지 않습니다 — 재부팅해야 0에서 시작합니다.

## 7. 빌드·적재 관련

### `insmod`가 `Invalid module format`으로 거부

실행 중인 커널과 **정확히 같은 소스트리**로 크로스컴파일해야 합니다. 버전
문자열만 같아도 안 되고, vermagic과 per-symbol CRC(`MODVERSIONS`)가 다 맞아야
합니다. 자세한 절차는 `docs/pi-bringup-guide.md` 참고.

### `make`했는데 아무것도 컴파일 안 됨

```
make[1]: 디렉터리 '...' 들어감
make[1]: 디렉터리 '...' 나감          ← CC/LD 줄이 없음
```
소스가 안 바뀐 것으로 판단해 아무것도 안 한 겁니다. **소스 복사가 실제로
됐는지 확인**하세요:
```sh
grep -c "찾을 문자열" cc1101_main.c
```
정상 빌드면 `CC [M] ... cc1101_main.o` / `LD [M] ... cc1101.ko`가 찍힙니다.

### `dtc`가 `syntax error`

`.dts`에서 `#include <...>`를 쓰면 안 됩니다. `dtc`는 C 전처리기가 아니라서
이 구문 자체를 못 읽습니다. 상수를 리터럴로 직접 쓰세요
(예: `GPIO_ACTIVE_HIGH` → `0`).

### `dev_dbg` 로그가 `dmesg`에 안 보임

이 커스텀 커널은 `CONFIG_DYNAMIC_DEBUG`가 꺼져 있어
`/sys/kernel/debug/dynamic_debug/control`이 아예 없습니다. 진단이 필요하면
임시로 `dev_warn`으로 올려서 확인하고 **반드시 되돌리세요**(패킷마다 커널
로그가 찍혀 운영에 부적합).

### `/dev/spidev0.0`이 안 보임

`dtoverlay=cc1101`이 활성화돼 있으면 우리 커널 모듈이 SPI 칩셀렉트를 차지해서
기본 `spidev` 드라이버가 바인딩되지 않습니다. 둘은 **동시에 못 씁니다.**
```sh
# spidev 모드로
sudo sed -i 's/^dtoverlay=cc1101/#dtoverlay=cc1101/' /boot/firmware/config.txt
# 커널 드라이버 모드로
sudo sed -i 's/^#*dtoverlay=cc1101.*/dtoverlay=cc1101/' /boot/firmware/config.txt
sudo reboot
```

## 8. 진단 기법 모음

### 8-1. 교차 테스트로 TX/RX 분리

"안 된다"만 알고 송신인지 수신인지 모를 때 **역할을 바꿔서** 테스트합니다.
두 보드는 독립적이라 **한쪽만 spidev 모드로 두는 것도 가능**합니다.

- A(커널) 송신 → B(spidev) 수신이 되면 → **커널 TX는 정상, RX가 문제**
- 이걸로 범위가 절반으로 줄어듭니다. 실제로 이 테스트가 결정적이었습니다

### 8-2. 통제 실험 — 검증된 기준점과 비교

`SpidevTransport`(유저공간 폴링 방식)는 소프트웨어 큐 없이 칩 FIFO를 직접
읽는 구조라, **"하드웨어냐 커널이냐"를 가르는 기준점**으로 유용합니다.
같은 물리 상태에서 이쪽이 되면 하드웨어는 정상입니다.

### 8-3. A/B 테스트로 내 수정 검증

내가 넣은 수정이 원인인지 의심되면 **이전 버전을 다시 빌드해서** 비교하세요.
```sh
git show <이전커밋>:cc1101_main.c > /tmp/old.c
# /tmp/old.c를 배포해서 같은 테스트 반복
```
실제로 이 방법으로 제 수정이 무죄임을 확인했습니다(진짜 원인은 안테나였음).

### 8-4. 한 번에 하나씩만 바꾸기

안테나·전원·오버레이·모듈을 동시에 만지면 어떤 변경이 뭘 바꿨는지 추적이
안 됩니다. 실제로 이 때문에 제 수정이 범인인 줄 알고 A/B 테스트까지 돌렸습니다.

### 8-5. 파일 무결성은 해시로 확인

"1067/1067 받았다"는 **패킷 개수**일 뿐입니다. CRC는 패킷 단위 검사라 순서
뒤바뀜·중복·특정 청크 유실은 CRC를 다 통과하고도 파일을 깨뜨립니다.

```sh
sudo ./ota_smoke_recv /dev/cc1101 recv.bin
# 전송 후 양쪽에서
sha256sum 원본.bin ; sha256sum recv.bin
```
