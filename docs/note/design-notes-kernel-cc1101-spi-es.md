## gateway-ota / ota-protocol 연결 지점

- `/dev/cc1101` ioctl 인터페이스는 `cc1101_ioctl.h`에 정의 — `gateway-ota`의
  `Cc1101Transport`(아직 스텁)가 이걸 그대로 가져다 씀
- OTA 패킷 자체의 포맷(`ota_protocol.h`)은 이 드라이버가 몰라도 됨 — 드라이버는
  바이트를 그대로 옮기기만 하고, 패킷 해석은 `gateway-ota`/`firmware-esp32` 쪽 담당
  (자세한 담당 범위 구분은 `gateway-ota`의 design notes 5절 참고)

## OTA도 채널 호핑 필요 — 아직 시작 못 함, ESP32 쪽 알고리즘 대기 중 (2026-08-11)

### 배경

원래 `firmware-esp32`의 `fsm-design.md`(2026-08-10 결정)는 "OTA는 음성 호핑 스케줄을
이탈해서 고정 채널로 받는다"는 전제였음(`FSM_STATE_FHSS_SYNC` 상태까지 삭제하면서
반영됨). 그런데 이후 요구사항이 바뀌어서 **OTA도 호핑해야 함** — 이유(간섭/재밍 회피,
규제 요건 등)는 아직 구체적으로 안 물어봤고, 결과만 전달받은 상태. 이렇게 되면
`fsm-design.md`의 2026-08-10 결정도 다시 뒤집어야 할 가능성이 있음(ESP32 담당자와
확인 필요).

### 지금 상태 (확인함, 2026-08-11)

- **커널 드라이버(`kernel-cc1101-spi`, 이 레포)**: `CC1101_IOC_SET_CHANNEL`/
  `CC1101_IOC_SET_FREQ`로 "채널 하나를 지금 바로 설정"만 가능. 정해진 타이밍에
  맞춰 스스로 채널을 계속 바꾸는 호핑 타이머/시퀀스 로직은 전혀 없음. **아직
  작업 시작 안 함.**
- **ESP32 쪽 (`firmware-esp32/fhss-ota-radio/components/fhss_core`)**: 통신 담당
  팀원이 호핑 관련 작업을 진행 **중**이지만, 핵심인 "시드+홉 인덱스 → 다음 채널"
  계산 로직(`fhss_hop_sequence.h/.c`)은 아직 빈 스텁 파일 상태로 확인됨. 타이밍
  판정 쪽(`fhss_timing_window`, 수신 시각이 예상 범위 안인지 판정)만 부분 구현됨.

### 왜 지금 바로 커널 드라이버에 구현을 못 넣는가

호핑 시퀀스 알고리즘(시드로부터 다음 채널을 계산하는 공식)은 라즈베리파이와
ESP32 **양쪽이 정확히 똑같이 계산**해야만 의미가 있음 — 한쪽이라도 다르게 구현하면
서로 다른 채널에 가 있어서 아예 못 만남. 이건 `ota_protocol.h`/`cc1101_ioctl.h`처럼
양쪽이 합의한 명세가 있어야 하는데, 그 명세(알고리즘)가 아직 ESP32 쪽에서도
확정 전이라 지금 커널 드라이버에 뭔가 구현하면 그냥 추측성 코드가 됨(이 프로젝트가
계속 피해온 패턴 — `firmware-esp32`의 `rf_transport` 관련 TODO들도 같은 이유로
비워둠).

### 다음 작업 (순서대로)

1. ESP32 쪽 `fhss_hop_sequence` 완성 대기 (통신 담당 팀원)
2. 완성되면 그 알고리즘 명세를 확인 — 시드 생성 방식, 채널 개수/간격, 홉당
   체류 시간(dwell time) 등
3. 커널 드라이버에 새 ioctl 추가 (예: `CC1101_IOC_START_HOP`로 시드/설정 전달,
   `CC1101_IOC_STOP_HOP`) + 이걸 구동할 hrtimer 기반 채널 전환 로직 구현
4. `cc1101_ioctl.h`가 바뀌면 `gateway-ota`가 들고 있는 사본
   (`OTA_System/transport/cc1101_ioctl.h`)도 같이 갱신 필요
5. `firmware-esp32`의 `fsm-design.md`(OTA 고정 채널 전제) 재검토도 같이 필요

## 2026-08-16 — 실기기 첫 성공까지, 그리고 그 과정의 오판들

이날 `/dev/cc1101`로 51200byte / 1067청크 전량 수신에 처음 성공했다
(1067/1067, 디코딩 실패 0건). 결론보다 **틀렸던 추론들**이 다음에 더
쓸모 있을 것 같아 같이 남긴다.

상세한 변경 내역과 담당자 인수 사항은 `docs/driver-changes-handoff-2026-08-17.md`,
증상별 대처는 `docs/troubleshooting-cc1101.md` 참고.

### 왜 내가(OTA 담당) 이 드라이버를 건드렸나

OTA 실기기 검증을 하려면 `/dev/cc1101`이 동작해야 했는데, 진행하다 보니
드라이버 쪽 버그가 연달아 나왔다. 남의 코드라 부담스러웠지만 검증을
멈출 수 없어서 고쳤고, 대신 **인수 문서를 따로 만들어 리뷰받는 방식**을
택했다. 다음에 비슷한 상황이 오면 같은 방식이 좋을 것 같다 —
"고치지 않고 기다리기"와 "고치고 조용히 넘어가기" 사이의 선택지로.

### 오판 1: "GDO2 펄스가 짧아 인터럽트가 못 잡는다"

한동안 이 가설로 문서에 *"오실로스코프 필요"* 라고 미해결 처리해뒀다.
**실제 원인은 수신측 안테나 불량이었다.** 계측 장비가 필요하다고 결론내는
순간 진단이 멈춰버렸는데, 정작 필요했던 건 안테나 교체였다.

교훈: **"장비가 없어서 더 못 한다"는 결론은 의심해볼 것.** 그 앞에 더 싼
검증이 남아있을 수 있다.

### 오판 2: "MCSM1 자동 복귀를 믿고 수동 SRX를 없애도 된다"

`cc1101_gdo0_thread()`의 TX 완료 경로에서 `cc1101_enter_rx()`를 제거했다.
논리는 그럴듯했다 — `MCSM1=0x3F`는 TXOFF_MODE=11(송신 끝나면 자동 RX 복귀)
이므로 수동 `SRX`는 중복이라고 봤고, 유저공간 구현에서 유사 증상을 같은
방식으로 고친 전례도 있었다.

**실측 결과 송신측 `cc1101-gdo0` 카운트가 7,728만 회까지 치솟았다**
(인터럽트 폭주). 폭주는 송신한 쪽에서만 발생하고 수신 전용 보드는 정상
(`gdo0=6`)이었다. 되돌리자 즉시 정상화.

이 커밋을 **`[미검증]`으로 표시해둔 것이 진단에 결정적이었다.** "해결함"
이라고 적어놨다면 의심 대상에서 빼놓고 한참 헤맸을 것이다.

교훈: **"이 변경이 왜 맞는지"에 대한 논증과 "실제로 그런지"에 대한 증거는
완전히 다른 것이다.** 전자만 있으면 그렇다고 적어야 한다. 그리고 칩 상태는
소프트웨어가 명시적으로 확정시켜야 하고, 하드웨어의 자동 동작에만 기대면
안 된다.

### 오판 3: "커널 드라이버 코드가 문제다"

수신이 안 되는 걸 계속 드라이버 버그로 몰아갔는데, 진짜 원인은
**팀원들과 싱크워드가 겹쳐서(`0xD3/0x91`, TI 레퍼런스 기본값) 남의 트래픽이
RX 큐를 채우고 있던 것**이었다. `dmesg`에서 `46 48 53 53`("FHSS")로 시작하는
패킷을 보고서야 알았다.

교훈: **원인 후보에 "우리 시스템 밖"을 넣어둘 것.** 같은 대역을 쓰는 다른
장비가 있는 환경이면 특히.

### 이번에 만든 것 — `tools/cc1101_diag.c`

추측만 반복하다가 `CC1101_IOC_READ_REG`/`GET_STATUS`로 **칩 내부를 직접 읽는
도구**를 만들자 단번에 범위가 좁혀졌다. 레지스터 17개가 기대값과 일치하고
`MARCSTATE=0x0D(RX)`인 걸 확인하니 "설정 문제 아님 / 칩은 정상"이 확정되고,
남은 후보가 물리 계층과 큐 관리로 줄었다.

교훈: **RF 디버깅은 추론보다 계측이 압도적으로 빠르다.** 진단 도구를 먼저
만드는 게 돌아가는 길처럼 보여도 실제로는 지름길이다.

### 설계 결정: RX 큐가 찼을 때 오래된 것부터 버림

기존 코드는 자리가 없으면 **방금 받은** 패킷을 버렸다. 그러면 한 번 차는
순간부터 영원히 새 패킷이 못 들어와 수신이 완전히 마비된다(실제로 이 상태에
빠졌다). 통신에서는 오래된 데이터가 새 데이터보다 가치가 낮으므로 지나간
것을 밀어내는 쪽으로 바꿨다.

**다만 이건 용도에 따라 다를 수 있다.** 실시간 스트림(음성)에는 drop-oldest가
맞지만, 손실이 치명적인 용도라면 반대일 수 있다. 이 드라이버를 공유하는 다른
기능이 있다면 정책을 분리해야 할 수도 있어서 인수 문서에 판단 항목으로 넣었다.

### 채널 이동은 검토했다가 안 씀

다른 팀과 물리적으로 분리하려고 `CHANNR` 변경을 검토했는데, 싱크워드 분리로
충분해서 채널 0을 유지했다. 대신 **나중에 위험한 실수를 막기 위해 제약을
주석으로 남겼다**: 국내 433MHz ISM 밴드(433.05~434.79MHz) 때문에 **채널 4가
상한**이고, 큰 값(예: 200)은 473.92MHz로 CC1101 지원 밴드(387~464MHz)조차
벗어나 PLL이 락을 못 걸어 송수신이 통째로 죽는다.

### 남은 것

- **임시 디버그 로그 원복** (`dev_warn` → `dev_dbg`). 이 커스텀 커널은
  `CONFIG_DYNAMIC_DEBUG`가 꺼져 있어 `dev_dbg`가 `dmesg`에 안 보여서 승격해뒀다.
  원인 파악이 끝났으니 되돌려야 하는데, 지금 상태로는 패킷마다 로그가 찍혀
  운영에 부적합하다.
- **수신 처리량** — 송신 청크 간 대기 40ms가 필요하다. 10ms에서는 수신이 못
  따라가 패킷 경계가 밀렸다(깨진 패킷 꼬리에 다음 패킷의 프리앰블 `AA AA AA` +
  싱크워드 `2D D4`가 딸려 들어옴). `out_rearm`에서 `SFRX` 없이 `SRX`만 하는 게
  관련 있을 수 있다 — 유저공간 구현은 매번 `SIDLE; SFRX; SRX`로 완전히 비우고
  재시작한다.
- **채널 호핑** — 위 2026-08-11 항목 그대로. ESP32 알고리즘 대기 중.
