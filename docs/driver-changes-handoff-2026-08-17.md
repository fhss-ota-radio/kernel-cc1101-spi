# cc1101 드라이버 변경사항 인수 문서 (2026-08-17)

| 항목 | 내용 |
|---|---|
| 작성자 | OTA 송신/Qt 담당 (gateway-ota) |
| 받는 분 | **cc1101 커널 드라이버 담당자** |
| 브랜치 | `feature/cc1101_V1` |
| 왜 제가 드라이버를 건드렸나 | OTA 실기기 검증을 하려면 `/dev/cc1101`이 동작해야 했는데, 진행 과정에서 드라이버 쪽 버그가 여러 개 나와서 부득이 수정했습니다. **리뷰해주시고 방향이 다르면 말씀해주세요.** |
| 최종 상태 | **실기기 2대로 51200byte / 1067청크 전량 수신 성공 (1067/1067, 디코딩 실패 0건)** |

## 0. 먼저 — 팀 전체에 영향 있는 변경 2가지

### ① 싱크워드가 바뀌었습니다 (가장 중요)

`SYNC1/SYNC0`을 팀 공용 기본값 `0xD3/0x91` → **OTA 전용 `0x2D/0xD4`** 로 변경했습니다.

**이유**: 우리 수신기에 다른 팀 장비의 패킷이 그대로 잡혔습니다.
```
46 48 53 53 01 01 00 00 ...    ← ASCII로 "FHSS"
A5 01 02 00 02 00 00 14 14 ... ← 49byte짜리, 다른 프로토콜
```
다들 TI 레퍼런스 기본 설정을 그대로 쓰다 보니 **433.92MHz + 싱크워드까지 전부 겹쳐** 있었고, 남의 패킷이 CRC까지 통과해 드라이버 RX 큐(512byte)를 가득 채워서 **우리 패킷이 도착해도 전부 폐기**됐습니다. 원인 찾는 데 하루가 걸렸습니다.

CC1101은 싱크워드가 다르면 **하드웨어 단에서 무시**합니다(인터럽트도 안 울리고 FIFO에도 안 들어옴). 소프트웨어 필터링보다 깨끗하고 CPU/큐 부담이 0입니다.

> **⚠️ 이 드라이버를 쓰는 다른 기능이 있다면 통신이 끊깁니다.**
> 음성 등 다른 용도로도 이 드라이버를 공유하고 있다면, 용도별로 싱크워드를
> 분리하는 방식이 맞는지 함께 정해야 합니다. 지금은 드라이버 기본값 자체를
> 바꿔놨는데, 필요하면 **ioctl로 런타임에 설정하는 구조**로 빼는 게 나을
> 수도 있습니다 — 판단 부탁드립니다.

> **[별건] 누가 어떤 주파수/싱크워드/채널을 쓰는지 정리된 표가 없습니다.**
> 이번 일이 그것 때문에 생겼으니 만들어두면 좋겠습니다.

### ② `gateway-ota`와 값이 짝을 이룹니다

`gateway-ota/OTA_System/transport/spidevtransport.cpp`의 레지스터 배열에도 같은 싱크워드가 들어가 있습니다(유저공간 우회 구현이라 자체적으로 칩을 설정함). **한쪽만 바꾸면 두 경로가 서로 통신하지 못합니다.** 값 변경 시 양쪽을 같이 보셔야 합니다.

## 1. 변경 목록

| # | 커밋 | 내용 | 검증 |
|---|---|---|---|

| 4 | `32d2a34`, `6340e75` | **임시** 디버그 로그(`dev_dbg`→`dev_warn`) | ⚠️ **되돌려야 함** |
| 5 | `dae7edb` | 싱크워드 `0x2D/0xD4` | ✅ 실기기 |

### 1번 — `cc1101_remove()` 반환타입

커널 6.5+부터 `spi_driver.remove` 콜백이 `void`를 요구합니다. 소스 주석에 이미 안내가 있었는데 반영이 안 돼 있어서 크로스컴파일이 `incompatible pointer type`으로 실패했습니다.

### 2번 — `.dts`의 `#include`

`dts/cc1101-overlay.dts`가 `#include <dt-bindings/gpio/gpio.h>`를 쓰고 있었는데, `dtc`는 C 전처리기가 아니라서 이 구문 자체를 못 읽고 syntax error를 냅니다. 그 헤더가 정의하는 `GPIO_ACTIVE_HIGH`(=0)를 리터럴로 직접 썼습니다.

### 3번 — 하드웨어 주소필터 (`PKTCTRL1` `ADR_CHK`)

`cc1101_default_regs[]`의 `PKTCTRL1`이 `0x0D`(주소필터 켬)였습니다. CC1101의 `ADR_CHK`는 수신 패킷의 **첫 페이로드 바이트를 자기 `ADDR` 레지스터와 비교해서 안 맞으면 CRC 검사 전에 하드웨어에서 버립니다.**

그런데 `ota_protocol.h`의 모든 패킷은 첫 바이트가 **"패킷 타입"**(`OTA_PKT_START` 등)이지 주소가 아니라서, 대부분의 패킷이 하드웨어 레벨에서 걸러지고 있었습니다. → `0x0C`(필터 끔)로 변경.

**주소/라우팅 판단을 소프트웨어에서 하기로 한 근거**: CC1101의 `ADDR` 레지스터는 1byte뿐인데 우리 `device_id`는 3byte입니다. 애초에 `ota_protocol.h` 상위 계층(`session_id`, `device_id` 필드)에서 처리하도록 설계돼 있어서 하드웨어 필터가 불필요합니다. 나중에 필요해지면 기존 `CC1101_IOC_SET_ADDR_FILTER` ioctl로 켤 수 있습니다.

### 4번 — ⚠️ 임시 디버그 로그 (되돌려야 함)

`cc1101_handle_rx_packet()`의 `dev_dbg` 호출을 **`dev_warn`으로 임시 승격**했습니다. 이유는 이 커스텀 커널에 `CONFIG_DYNAMIC_DEBUG`가 꺼져 있어서 `dev_dbg` 로그가 `dmesg`에 전혀 안 보이기 때문입니다(`/sys/kernel/debug/dynamic_debug/control`이 아예 없음).

**원인 파악이 끝났으니 `dev_dbg`로 되돌리는 게 맞습니다.** 지금 상태로는 패킷마다 커널 로그가 찍혀서 운영에 부적합합니다. 어느 로그를 남기고 어느 걸 지울지는 담당자 판단에 맡기겠습니다 — 다음 항목들이 승격돼 있습니다:

- `[임시디버그] 패킷 큐에 넣음 (len=..., rssi_raw=..., first_byte=...)`
- `[임시디버그] CRC 오류, 패킷 폐기 (...)`
- `[임시디버그] GDO2 울렸는데 RXBYTES=0x.. (빈 FIFO)`

### 5번 — 싱크워드 (위 0-① 참고)

### 6번 — RX 큐 관리 2건

**(a) `cc1101_open()`에서 kfifo 비우기**

드라이버는 `probe()`에서 RX에 들어간 순간부터 계속 수신해 큐에 쌓지만, 유저 프로그램은 한참 뒤에 붙습니다. 그 사이 쌓인 건 이미 지나간 데이터라 쓸모없는데 자리만 차지해 **새 패킷이 들어올 자리를 막았습니다.**

**(b) 큐가 가득 차면 "새 패킷"이 아니라 "오래된 패킷"부터 버리기**

이전 코드는 자리가 없으면 방금 받은 패킷을 버렸습니다. 그러면 **한 번 차는 순간부터 영원히 새 패킷이 못 들어와 수신이 완전히 마비**됩니다. 실기기에서 실제로 이 상태에 빠졌습니다(남의 팀 패킷이 큐를 채운 뒤 우리 패킷이 하나도 안 올라옴).

통신에서는 오래된 데이터가 새 데이터보다 가치가 낮으니 지나간 것을 밀어내는 쪽이 맞다고 판단했습니다. 큐 내용이 손상된 경우(길이바이트와 실제 본문 길이 불일치) 통째로 초기화하는 방어 코드도 넣었습니다.

> 이 정책이 이 드라이버의 다른 사용처(예: 음성)에 부적합하면 말씀해주세요.
> 실시간 스트림에는 drop-oldest가 맞지만, 손실이 치명적인 용도라면 다를 수 있습니다.

### 7번 — 진단 도구 `tools/cc1101_diag.c`

`CC1101_IOC_READ_REG` / `GET_STATUS` ioctl로 **칩 내부를 직접 읽습니다.**

```sh
gcc -O2 -o cc1101_diag tools/cc1101_diag.c -I.
sudo ./cc1101_diag            # 현재 상태
sudo ./cc1101_diag --set-rx   # SET_RX 후 상태
```

- 핵심 레지스터 17개를 기대값과 비교 → SPI 쓰기가 실제로 반영됐는지 확인
- `MARCSTATE`(칩 상태머신) 출력 → `0x0D`면 수신 대기 정상

저희는 이 도구를 만들고서야 "설정 문제 아님 / 칩은 RX 정상"을 확정하고 범위를 좁힐 수 있었습니다. **RF 디버깅은 추론보다 계측이 압도적으로 빠릅니다.** 앞으로 문제 생기면 이걸 먼저 돌려보시길 권합니다.

### 8번 — ⚠️ 시도했다가 되돌린 변경 (기록 목적)

**`cc1101_gdo0_thread()`에서 TX 완료 시 `cc1101_enter_rx()` 호출을 제거했다가 되돌렸습니다.**

**제거했던 가설**: GDO0(`IOCFG0=0x06`)의 falling edge는 "패킷 끝"이지만 마지막 몇 바이트가 아직 안테나로 나가는 중일 수 있어, 그 순간 `SRX`를 강제하면 칩이 애매한 상태에 빠질 수 있다. `MCSM1=0x3F`(TXOFF_MODE=11)가 이미 "송신 끝나면 자동 RX 복귀"이므로 수동 `SRX`는 불필요하다고 봤습니다. gateway-ota의 유저공간 구현에서 유사 증상을 같은 방식으로 고친 전례도 있었습니다.

**되돌린 실측 근거**: 이 변경을 올린 뒤 송신측의 `/proc/interrupts`에서 `cc1101-gdo0` 카운트가 **7,728만 회**를 넘겼습니다 — 인터럽트 폭주(IRQ storm). 폭주는 **송신을 수행한 쪽에서만** 발생했고 수신 전용 보드는 정상(`gdo0=6`)이었습니다.

**결론: `MCSM1`의 자동 복귀만 믿으면 안 되고 명시적 `SRX`로 상태를 확정시켜야 합니다. 원래 코드가 맞았습니다.** 코드에 이 경위를 주석으로 남겨뒀습니다 — 나중에 같은 최적화를 다시 시도하지 않도록요.

## 2. 실기기 검증 결과

**환경**: 라즈베리파이 2대(pi24 송신 / pi06 수신), CC1101 433.92MHz, 채널 0

```
[smoke_send] 핸드셰이크 성공 — session_id=0x14eea8f3 totalChunks=1067
[smoke_send] 전송 중: 1067/1067
[smoke_send] 완료
[smoke_send] 응답 확인 종료 — 총 342개 수신

[smoke_recv] OTA_START ... imageSize=51200 totalChunks=1067
[smoke_recv] OTA_DATA seq=0 ... seq=1066 len=32
[smoke_recv] OTA_END ... (실제 받은 DATA 개수=1067)
```

**1067/1067, 디코딩 실패 0건, seq 연속(누락·중복 없음).**

> 송신 시 청크 간 대기 40ms를 줬습니다(`chunkDelayMs=40`). 10ms로는 수신이
> 송신 속도를 못 따라가 패킷 경계가 밀리는 현상이 있었습니다. 이 값을
> 낮추려면 수신 경로 최적화가 필요합니다 — 아래 3번 참고.

### 재현 방법

```sh
# 양쪽 파이: config.txt에 dtoverlay=cc1101, 재부팅 후
sudo insmod cc1101.ko
sudo ./cc1101_diag              # 레지스터/MARCSTATE 확인

# 수신측
sudo ./ota_smoke_recv /dev/cc1101
# 송신측
sudo ./ota_smoke_send /dev/cc1101 <bin파일> ffffff 40
```

## 3. 남은 과제 / 담당자 판단이 필요한 것

| # | 항목 | 비고 |
|---|---|---|
| 1 | **임시 디버그 로그 원복** (`dev_warn`→`dev_dbg`) | 위 1-4번. 운영에 부적합한 상태 |
| 2 | **싱크워드를 ioctl 런타임 설정으로 뺄지** | 다른 용도와 공유하는 드라이버라면 필요 |
| 3 | **drop-oldest 정책이 다른 용도에도 맞는지** | 위 1-6(b) |
| 4 | **수신 처리량 개선** | `chunkDelayMs` 40 → 더 낮추려면 필요 |
| 5 | `out_rearm`에서 `SFRX` 없이 `SRX`만 하는 것 검토 | 유저공간 구현은 매번 `SIDLE; SFRX; SRX`로 완전히 비우고 재시작함. 잔여물 누적 가능성 |
| 6 | GDO0/GDO2 배선표 정정 공유 | 전달받은 표(GDO0=GPIO25, GDO2=GPIO24)와 실기기가 **반대**. 레포 기본값(GDO0=**24**, GDO2=**25**)이 맞음 |

### 4·5번 부연

패킷 경계 밀림 증상(청크 간격 10ms일 때): 깨진 패킷 꼬리에 다음 패킷의 프리앰블(`AA AA AA`)과 싱크워드(`2D D4`)가 딸려 들어왔고, 디코딩 성공률이 4개 중 1개꼴이었습니다. 40ms로 늘리니 100%가 됐습니다. 수신이 송신을 못 따라가는 구조적 문제로 보이며, 5번(FIFO 완전 flush)이 관련 있을 수 있습니다.

## 4. 하드웨어 쪽에서 겪은 것 (참고)

- **안테나 불량** — 헐거운 게 아니라 안테나 자체가 죽어 있었고, 교체하니 즉시 해결. 이것 때문에 한동안 소프트웨어를 잘못 의심했습니다.
  - **진단 힌트: "송신은 되는데 수신만 안 된다"면 안테나를 먼저 의심하세요.** 송신은 안테나가 부실해도 근거리면 도달하지만, 수신은 미약한 신호를 잡아야 해서 훨씬 민감합니다.
- **원인 계층 가르는 기준** — `/proc/interrupts` 카운트가 **아예 안 올라가면 물리 계층**(안테나·전원·배선), **올라가는데 데이터가 깨지면 소프트웨어**입니다. 이 구분 하나가 시간을 가장 많이 아껴줬습니다.
- **브레드보드 전원모듈(MB102/HW-131)** — 3.3V 출력 지점이 여러 곳인데 서로 연결하면 발열합니다. 한 곳만 쓰고, 파이와 GND 공유 필수.
